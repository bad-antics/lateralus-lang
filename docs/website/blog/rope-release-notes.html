Edit release notes without flattening first

Release notes are edited in small increments. A flat string is convenient until each change copies the whole document. A rope keeps text in a tree of chunks, so the editing API can describe the operation without making the example depend on a particular storage layout.

Build one edit vector

The example starts with release notes, inserts a draft marker at the boundary after the word release, splits the result, deletes the original prefix, and asks for a short substring. The final length is the rope's character count.

// Run after stdlib/rope.ltl in the same compilation unit.
let doc = from_str("release notes")
doc = insert(doc, 8, "draft ")
print(to_str(doc))

let pieces = split_at(doc, 7)
print(to_str(pieces[0]))
print(to_str(pieces[1]))

doc = delete(doc, 0, 8)
print(to_str(doc))
print(substr(doc, 0, 5))
print(length(doc))

Read the result

Run the vector from the repository root with the pinned interpreter:

python tests/test_rope_release_notes.py -v

The expected output is:

release draft notes
release
 draft notes
draft notes
draft
11

The split operation returns two ropes. The left part is release, and the right part retains the leading space before the inserted draft text. Deleting eight characters removes the original release prefix, while substr reads the first five characters from what remains. The test compares these exact lines after joining the repository's current stdlib/rope.ltl with the example in a temporary compilation unit.

Why keep the check small?

A short vector makes every edit visible. It also keeps the tutorial honest about the current implementation. The test checks the public operations and their output, without making a performance claim or depending on an undocumented tree shape.
